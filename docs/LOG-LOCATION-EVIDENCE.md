# 지표 목표 위치와 복귀 알림 — 2026-11-03

## 구현 범위

`locations.mjs`는 공개 거점의 월드 좌표에서 부모 행성/위성의 월드 좌표를 빼서 로그 목표 좌표와 대조한다. XYZ의 3차원 오차가 **0.01m 이하**이고 한 거점만 일치해야 `coordinate-match`다. 이는 좌표 관측의 일치이며 전체 화물 명세 검증이나 내 함선 위치가 아니다.

- 가까운 거점 순위, Z축만 비교, 지명 유사도 또는 `zoneHostId`→공개 UUID 추정은 사용하지 않는다.
- 두 세계의 같은 상대 좌표, 다중 인스턴스 ID, ID 없는 후보는 보류한다. 부모 누락/중복/다른 항성계/행성·위성이 아닌 부모도 지원하지 않는다.
- 1cm 격자 해시의 이웃 27개만 조회한다. 같은 목록을 감시 주기마다 다시 읽거나 외부에 요청하지 않는다.
- 같은 실행 계약·정확히 같은 목표 ID의 수량 알림만 함께 표시한다. 숫자 접미사, API 주문 배열 순서, 같은 상품을 근거로 다른 목표에 거점을 복사하지 않는다.
- 같은 목표의 위치/역할/정의 충돌은 보류하고, 다른 총량 알림은 충돌로 표시한다. 과거 마커를 현재 위치로 쓰거나 계정 데이터를 바꾸지 않는다.
- `manifest:null`, `planning.allowed:false`는 유지한다. 실제 품목별 픽업/배송 할당, 상자 크기별 개수는 아직 확인되지 않았다.

## 공개 출처와 버전 한계

출처는 [Star Citizen Wiki API positions](https://api.star-citizen.wiki/api/locations/positions)다. 응답 1,840개 중 지원하는 부모 상대 좌표 항목은 615개다. 새 파일 `data/log-location-index.json`은 약 411KB이며 공개 ID·이름·부모·종류·항성계·XYZ, 수집 시각 및 원응답 SHA-256을 담는다. 사용자 로그·실행 ID·계정 정보·번역 원문은 넣지 않는다.

[제공자 컨트롤러](https://github.com/StarCitizenWiki/API/blob/fab953d20b6d6c485c2430066e0a03a7db6fbbb6/app/Http/Controllers/Api/Game/StarmapPositionController.php)는 `version` 쿼리를 처리하지 않고 좌표 스냅샷을 반환한다. 따라서 미션 API의 버전을 빌려 붙이면 안 된다. 새 좌표 목록의 `version`은 **null**, UI는 게임 빌드 일치 미확인으로 표시한다. 수집일은 버전 검증이 아니다.

재생성은 공개 응답을 받은 다음 아래 명령으로 한다. 입력 수집 시각은 실제 값을 기록한다. 잘못된 데이터는 기존 파일을 교체하지 않는다. 자동 갱신 워크플로는 아직 없다.

```sh
node scripts/build-log-locations.mjs --input <public-positions.json> --output data/log-location-index.json --retrieved-at <실제-ISO-수집시각>
```

다른 도구 조사에서 [SuperCargo markerResolve](https://github.com/AquatikJustice/SuperCargo/blob/6d088e78255de4e5cd07e6dd9b63fa6e671ee9bc/src/shared/markerResolve.ts)의 Z축 비교를 확인했다. 해당 구현은 복사하지 않았다. STAM은 공개 XYZ와 부모 좌표를 이용해 독립 구현했으며, 다른 앱의 동작 자체를 CIG 승인 근거로 삼지 않는다.

기존 33개 로그(98,100,426바이트) 엄격한 UTF-8 재생: 운송 계약 104개, 고유 목표 302개, 좌표 일치 164개/미일치 138개. 손상 줄 646개 제외. Cloud에서 재생·대조 약 1.2초; 실게임 부하 측정이 아니다. 164개 전부를 실제 운항으로 검증한 것은 아니며 공개 좌표 일치 집계다.

## 배송만으로 종료됐는데 복귀가 표시된 사례

사용자 제공 로그에서 정의 `b9144071-cf16-4012-a33f-a39d42cdc260`의 DEAD SAINTS 중형 운송을 확인했다. 아래 시각은 UTC다.

- 2026-10-22 15:07:12.232: CRU-L5 Beautiful Glen으로 돌아가라는 수량 없는 목표 알림.
- 15:08:54.539: 마지막 배송 목표 `dropoff_…_4` 완료.
- 15:08:54.587: 같은 계약 `EndMission CompletionType[Complete]`.
- 15:08:54.591: 같은 계약의 완료 HUD 알림.

복귀 목표 자체의 완료 상태는 이 기록에서 확인되지 않았다. 사용자의 ‘복귀하지 않아도 배송으로 완료’ 관측과 부합하지만, 복귀 안내의 생성 원인이나 모든 유형의 복귀 의무가 없다는 결론으로 일반화하지 않는다. 다른 복귀 알림 2개는 호위/전투훈련 미션이라 운송 목록에 넣지 않는다.

이전 파서는 SCU 없는 목표 알림을 버렸다. 이제 `objective-notice-observed`로 원문·목표 ID·시각·출처를 보존한다. 수량, 필수 경로, 복귀 의무, 재참여 상태를 생성하지 않는다. UI는 별도 접힘 영역에 표시하며, 충돌 없는 본인 Complete 종료가 있을 때 완료 관측을 함께 안내한다. 기존 엔진의 자동 귀환 금지 정책은 그대로다.

## 검사와 남은 일

- Node 22.23.4 / 26.13.0 전체 테스트 각각 **184개 통과, Windows 전용 1개 건너뜀**. 8개 위치 검사와 1개 복귀/방문 알림 회귀 검사 추가. 최초 제한된 네트워크 샌드박스에서는 HTTP 테스트가 실패했으며 로컬 HTTP 허용 환경에서 전체 재실행 통과했다.
- Node 26 loopback + Chromium: 두 계약의 6개 지표 거점, 정확한 목표 수량 연결 2개, 계산 0 유지, 목록 각각 1회 요청, 외부 요청 없음, 390px 넘침/JS 오류 없음. 좌표 목록 404도 미확인으로 표시하며 계약 카드는 유지.
- 과거 실제 복귀 사례 재생: 알림 보존·본인 완료 표시·계약 재활성화 없음 확인. 새 Windows 앱 화면/실시간 게임 수락으로 이번 위치 코드를 검증한 것은 아니다.
- 다음: 우주 거점의 좌표계 근거, 실제 주문↔목표 할당, 실물 상자 분포. 근거를 확보하기 전 수치나 필수 복귀를 추정해 적재/경로를 활성화하지 않는다.
