## 2. 제품 목적과 사용 흐름

Star Citizen의 운송 미션을 여러 개 수주했을 때 스크린샷을 올리면 미션별 화물·픽업지·배송지를 정리하고, 방문 순서·적재 위치·예상 시간과 수익을 안내하는 팬 도구다. 기본 사용에 유료 AI API를 요구하지 않는다.

현재 흐름:

1. 사이트 접속 → 운항 파트너 선택 → 선택한 인물의 인사.
2. 함선 선택 → 드라이브 초기 설정 → 출발 위치 확인.
3. 미션 스샷 여러 장 업로드·붙여넣기 → 브라우저 OCR 자동 입력.
4. 카드 체크 → 외부 버튼으로 일괄 경로 계산. 상자 구성 확인·총수량 확인·최대치 기준을 구분한다. 최대치 예상은 명시적으로 허용하고, 실제 수량·상자 구성 직접 입력은 선택사항이며 해당 계약에만 적용한다. 과거 구성 자동 기억·재사용은 제거됐다.
5. 간편 경로 / 상세 적재 계획 → 지도·거점·적재 안내.
6. 출항 → 거점별 접수/배송 완료 기록 → 다음 구간 안내 → 운항 완료.

새로 접속해 파트너 선택 창이 나와도 기존 미션과 운항 기록을 임의로 비우면 안 된다.

## 3. 가장 중요한 확정 요구사항

### 미션 화물의 소유권

- 같은 품목·같은 크기의 상자라도 수주한 미션이 다르면 다른 화물이다. 다른 미션 상자로 제출을 대체할 수 없다.
- 미션 이름·품목·배송지가 같다는 이유로 독립 수주를 합치지 않는다. `missionId`, `shipmentId`, `boxId`의 연결을 보존한다.
- 상자 구성 템플릿은 **구성만** 재사용한다. 이전 수주의 ID나 상자 소유권을 새 미션에 복사하지 않는다.
- 진행 중 실린 상자를 재계산할 때 임의로 다른 셀로 옮기지 않는다. `resume`의 aboard/fixed packing을 보존한다.
- 현재 자동 적재는 모든 함선에서 미션별 그리드를 우선 사용하되, 공간이 부족하면 빈 셀을 공유한다(2026-10-30 재방문 수정). 이때도 상자는 독립 ID와 셀을 가진다. `shareGrids=false`로 전용 그리드를 강제할 수 있다. '그리드 공유'를 '미션 병합'으로 바꾸지 않는다.
- 적재 색은 **배송 순서에 따른 목적지 색**이다. 색만으로 미션 소유권을 판단하지 말고 ID·목적지·구역 정보를 함께 표시한다.

### 화면과 지도

- 설명은 사용자와 한국어로 한다. 앱의 문장은 자연스러운 존댓말, 필드·버튼은 간결한 표현을 사용한다.
- 실제처럼 정확하게 만들 수 없는 함선 외형은 표시하지 않는다. 현재는 **그리드만** 표시한다.
- 모든 함선(Hull B 포함)은 회전 가능한 3D 화면 하나를 사용한다(2026-10-30 사용자 결정으로 Hull B 좌현/우현 분할 폐지). 앞/뒤/좌현/우현/위/출입구 표시를 유지한다.
- 화물이 붙는 방향은 함선마다 다르다(2026-10-30 사용자 확인): 평평한 화물칸은 바닥부터 위로, Hull B·Hull C는 중심축 쪽 면에 붙어 바깥(옆)으로, RAFT는 위에서 아래로. `ships.mjs`의 `STACK_BY_SHIP`·`withStacking`이 그리드를 붙는 면 기준 좌표로 바꾸고 3D 화면은 그리드 회전으로 되돌려 표시한다. 다른 함선은 확인 전까지 바닥 기준.
- 빛 번짐(bloom)은 끈다. `bloom.mjs`는 톤 매핑에도 쓰이므로 파일 자체를 지우는 것은 별개 문제다.
- 항성은 흰색으로 날아가지 않게 따뜻한 크림색·금빛 표면 무늬와 얇은 코로나를 사용한다.
- 배경: 파이로는 주황·호박빛(새빨간색 금지), 스탠턴은 청록빛 남색, 닉스는 차가운 군청색·보랏빛. 지명·경로선 가독성을 유지한다.
- 퀀텀 경로는 직선 중심이며 천체를 통과할 때만 비켜간다. 현재 구간은 주황색, 구간 순서대로 나타나는 연출을 유지한다.
- 확대·축소·이동 범위를 제한한다. 행성계 사이를 하나의 좌표계에서 직선 거리로 계산하지 않는다. 확인된 게이트웨이와 점프 연결을 사용한다.
- UI에 자동 원점 복귀를 다시 넣지 않는다. 배송 완료로 운송이 끝나는 현재 정책을 따른다. 엔진의 `includeReturn`은 옵션으로 남아 있지만 앱은 false로 고정한다.

### 운항 파트너

선택 순서는 브리지 오퍼레이터(`aide`) → 수석 항해사(`standard`) → 밀수 브로커(`broker`)다. 지도 왼쪽 위 STARMAP 아래 초상화 카드로 선택창을 연다. 관제 모드에서도 동일하다.

- 오퍼레이터: 같은 행성권에서 가까운 화물을 모은 뒤 배송하며, 떠난 후 실은 화물을 모두 배송하기 전 다른 권역에서 새 픽업을 하지 않는다. 소량·간단한 계약의 완료 우선. `delivery-first.mjs`에서 우선 계약을 정하고 가까운 중간 픽업을 허용한다. 다른 배송지의 화물도 실을 수 있지만 우선 계약 적재를 방해하면 안 된다. 추가 작업·우회의 누적 시간은 계약 예상 이동 시간의 25%, 최대 5분 이내다.
- 수석 항해사: 기존 `route-search.mjs`/`route-cost.mjs` 묶음 운송을 유지하며 행성권 재방문 횟수를 거리·시간보다 먼저 비교한다. 거리가 조금 늘어도 대기권 재진입·재착륙을 줄이는 우선순위다. 파트너에 따른 `routePolicy` 분기는 경로 선택에서만 적용하고 실제 적재·진행 중 화물 위치 보존은 공유한다.
- 브로커: 파이로 초상화와 준비 중 소개만 제공한다. 소개 화면 다음 진행 버튼은 비활성화하며 활성 운송 파트너 값에 저장하지 않는다. 실제 무역 API 연동은 아직 구현하지 않았다. 옛 `military` 선택은 수석 항해사로 해석한다.

소개는 각자의 말투로 기능을 설명한다. 출발지는 한글·영어 부분 검색 → 목록 선택 → 재확인 순서다. 상자 구성은 저장값/미션 최대 크기/기본 가정값으로 미리 채우고, 추정값을 명시한다. 변경 없이 진행한 예상 구성은 실제 구성으로 저장하지 않는다. 운항 목록은 상자 크기별 개수를 표시한다.


### 2026-11-02 출발지·미션 구성·냉동포드 보완

- `route-departure.mjs`는 기존 탐색 결과 앞에 출발 단계만 추가한다. 첫 이동선과 시간은 기존 구간 그대로이며, 운항 시작 위치는 첫 픽업지가 아닌 `settings.startId`다. 재계산 시 실제 완료 위치·게이트웨이 출구를 사용한다.
- 안내창에 미션 유형·구성 출처·품목별 계산·픽업지를 표시한다. 저장값을 위키 기준으로 되돌리는 선택은 해당 계약에만 적용하며 공유 레시피를 지우지 않는다.
- **냉동포드는 1개=1 SCU, [1, 0.5, 2] 셀**. 두 개 적층 시 일반 2 SCU 상자와 같은 높이. 홀수 적층 위 또는 높이가 다른 지지면에 걸쳐 일반 상자를 올리지 않는다. 엔진은 포드가 있을 때만 세로 반 셀 해상도를 사용하며 각 포드의 소유권·개수를 유지한다. Wiki `reportedVolumeScu:2`는 원본 메타데이터로 보존하고 운송량을 2배로 만들지 않는다.

## 4. 실제 미션 예시 — 수량 의미를 바꾸지 말 것

스샷에 보이는 SCU는 배송 총량이고 실제 상자의 크기·개수와는 다르다. `0/32 SCU`의 32를 32 SCU 상자 하나라고 단정하면 안 된다.

확인된 예시:

- 발주처: 레드 윈드 노선화물. 미션 제목은 원본 화면에서 잘려 있어 최초에는 직접 확인이 필요하다.
- 픽업: 어거스트 던로우 우주공항 → 데이터 위치 `Orison`으로 매칭.
- 배송: `Canard View`(카나드 뷰), `Jackson's Swap`(잭슨 교환소).
- **배송지마다** 함선 탄약 32 + 수소 32 + 의약품 20 = **84 SCU**.
- 사용자가 확인한 **배송지 하나의 실제 상자 구성**: `16 SCU × 4 + 2 SCU × 10 = 84 SCU`, 14상자.
- **미션 전체**: 168 SCU, `16 SCU × 8 + 2 SCU × 20`, 28상자.
- 각 크기의 상자가 어떤 품목인지까지는 확정되지 않았다. 품목별 크기를 지어내지 말고 배송지 묶음으로 계획한다.

최초 구성도 위키 최대 규격으로 미리 채우며, 사용자는 다른 부분만 수정한다. 수동 구성은 같은 품목 조합에 재사용하고 출처를 구분한다. 원본 스크린샷 자체는 저장소에 포함하지 않는다.

### 경로·적재의 범위

- 정상적인 목표 사용량은 약 10개 동시 미션. UI 미션 상한 30개, 상세 운송 묶음 상한 64개, 간편 경로는 48개 구간. 과거 문서의 '32개 묶음', 'Hull B만 지원' 설명은 최신 구현과 다르다.
- 휴리스틱/제한된 빔 탐색으로 전역 최적 경로를 보장하지 않는다. 그리드 공유 여부에 따라 용량이 남아도 추가 운송이 필요할 수 있다.
- 출발 시 이미 실린 화물은 일반 새 계획에서 자동 인식하지 않는다. 진행 중 `resume`만 현재 기록된 적재를 유지한다.
- 자동 하역 순서는 권장안이다. 입구·사람 이동·중량·실제 스냅·차폐를 게임처럼 완전히 시뮬레이션하지 않는다.
- Hull B 기본은 16개 × 2×2×8 셀 = 512 SCU. 각 그리드의 실제 부착 좌표·회전은 개략일 수 있다. 1셀은 한 변 1.25m의 SCU 공간 단위다.
- Hull B의 16 SCU 세워 적재 금지는 그리드별 `noUpright`로 표현하며, 모든 함선·모든 상자에 일반화하지 않는다.

### 함선·드라이브 자동 설정

- 기준은 함선의 실제 드라이브 **슬롯 크기**다. 겉보기 함선 크기나 화물량으로 슬롯을 추측하지 않는다.
- S1 → Atlas, S2 → Hemera, S3 → Erebos. 그 외 슬롯은 데이터에서 확인된 기본 장착 드라이브.
- 초기 함선 선택 단계에서 `기본 장착 / 민수 A등급 / 사용자 설정`을 한 번에 고를 수 있다. 사이드바에서도 바꿀 수 있다.
- 사용자 설정은 평균 퀀텀 속도 직접 입력이다. 모든 시판 드라이브의 전체 선택 목록을 구현한 것은 아니다.
- 퀀텀 이동은 드라이브로 계산하고, 일반 비행·지상 접근은 SCM/NAV 성능으로 계산한다. 단순한 '큰 배는 느림' 배수를 추가하지 않는다.
- `performanceId`를 보존해 개인 그리드 프로필을 저장해도 원래 함선 성능을 사용할 수 있게 한다.
- 기본 접근 가정: 지상 30km를 SCM의 65%, 우주 거점 20km를 NAV 최고속도의 65%. 착륙·이륙 여유, 정렬·준비 여유, 정박·상자 작업 시간은 별도다. 이는 실제 대기권 성능이나 적재 질량을 재현한 데이터가 아니다.
- 지상 접근 거리·여유와 접근 평균은 수정 가능하다. `spaceDistanceKm`는 엔진 설정으로 존재하지만 현재 UI에서 별도로 노출하지 않는다.
- 좌표/드라이브 스냅샷의 속도는 m/s, 수동 평균 퀀텀 속도 입력은 km/s다. 단위 변환을 보존한다.
- 가감속 모델은 근사이며, 10 Gm 참조 시간 오차 15% 이내를 검사한다. 실제 이동 시간 보장 기능이 아니다.

컴퓨터를 재시작해도 동일 브라우저 프로필의 저장값은 보통 유지되지만, 다른 PC·다른 프로필·시크릿 모드와 공유되지 않는다. 브라우저 데이터 삭제 시 소실될 수 있다.

## 7. 웹앱 로그인·개인 설정 동기화 — 구현 완료

`account.mjs`·`sync.mjs`·`firebase-config.mjs`·`firestore.rules`를 사용한다. 게스트 사용, 이메일/Google 선택 로그인, 사용자별 저장, 게스트 데이터 가져오기, 충돌 선택, 계정별 수정 기록이 구현돼 있다. 사용자가 Firestore 규칙 게시와 피드백 수신을 확인했다. 계정 통계와 기록 초기화도 기존 동기화 경로를 사용한다.

게스트/계정 분리와 충돌 선택을 유지하고 다른 사용자의 데이터나 기존 진행을 조용히 덮어쓰지 않는다. 실제 계정·다른 기기 검증 여부는 최신 PROJECT_STATUS.md를 따른다. 이번 Codex 검증은 모의 로그인 화면/통계/초기화까지이며 실제 Google 로그인·원격 삭제 검증은 아니다. 관리자 자격증명과 비밀키를 저장소에 넣지 않는다.

## 8. 알려진 한계·다음 검증

- PC 미션 스크린샷의 OCR 정확도는 추가 실사용 검증이 필요하다. 노이즈가 있는 휴대폰 사진에서 모든 값이 자동으로 맞는다고 보장하지 않는다.
- AI 서버 코드와 모의 응답 테스트는 있지만 실제 API로 정확도를 검증한 상태는 아니다. 선택적 AI 경로의 미션 ID 갱신 로직은 신규 독립 수주를 덮어쓰지 않는지 재검토한다.
- 상자 구성 저장 키는 게임 버전·발주처·미션명·품목/수량 형태를 본다. 같은 이름의 다른 변형에서 잘못 적용되지 않는지 사례를 늘린다.
- 지도·성능의 버전이 달라지면 묵은 수치를 같은 버전이라고 표시하지 말고 성능 스냅샷도 갱신한다.
- 연료 탱크에 따른 항속거리, 실시간 주유/수리 가능 여부, 엘리베이터·패드 제한, 서버 대기열, 전투·날씨·대기권 저항은 완전 반영하지 않는다.
- 미션 추천/스태킹, 팀 공유, 게임 로그 자동 입력은 아이디어이며 완성 기능이 아니다.

## 9. Codex Cloud에서 실행·검증·배포

### 깨끗한 체크아웃

Node.js 22와 네트워크가 있는 환경에서 저장소 루트 기준:

```sh
node scripts/prepare.mjs
npm test
npm start
```

- npm 의존성 설치가 필수인 프레임워크 프로젝트가 아니다. 잠금 파일이 없는데 무조건 `npm ci`부터 실행하지 않는다.
- `prepare.mjs`는 없을 때만 `vendor/three.module.js`와 `data/locations.json`을 준비한다. 두 파일은 Git에서 제외된다.
- `ensure-three.mjs`는 고정 Three.js 파일의 SHA-256을 검증한다. `OrbitControls`와 라이선스는 저장소에 포함돼 있다.
- 정적 서버는 기본 4173 포트와 loopback을 사용한다. Cloud 미리보기 연결이 안 되면 먼저 포워딩·바인딩 요구사항을 확인한다.
- 브라우저 OCR은 CDN의 Tesseract와 언어 데이터를 받는다. 네트워크 차단과 OCR 버그를 구분한다.
- 개인 API 키 없이 지도·경로·적재·브라우저 OCR·테스트를 사용할 수 있다.

### 데이터 갱신

```sh
node scripts/refresh-data.mjs
node scripts/refresh-performance.mjs
npm test
```

좌표 출처는 `https://api.star-citizen.wiki/api/locations/positions`, 성능 출처는 같은 API의 vehicles/items다. 현재 기준 스냅샷은 `4.10.2-LIVE.12881860`, 좌표 731개와 확인된 점프 연결 2개다. 최신 실행에서는 실제 meta 값을 확인한다.

### 배포

`.github/workflows/pages.yml`이 main push / 수동 실행 / 매일 09:23 KST 예정 실행을 처리한다. 스케줄은 GitHub 사정으로 지연될 수 있다.

라이브러리 준비 → 직전 배포와 비교하며 좌표 검증 → `npm test` → 공개 파일만 묶기 → Pages 배포. 좌표 오류·대량 소실·점프 손실이면 기존 사이트를 잘못된 데이터로 교체하지 않도록 검증한다.

**소스 커밋 성공과 Pages 배포 성공은 별개다.** Actions 결과와 실제 사이트를 확인한다. 최신 main에 다른 변경이 생겼으면 보존하고 병합한다.

### 회귀 확인 목록

- 파트너 선택이 인사보다 먼저 나오고 사진 3개가 모두 표시되는가.
- 수석/장교/비서의 전체 안내와 운항 완료 문구가 바뀌는가.
- 파트너 변경·재접속으로 미션·운항 기록이 사라지지 않는가.
- Hull B / Zeus CL / Hermes와 소형·S3 함선 전환 시 그리드와 성능이 함께 바뀌는가.
- 기본 장착 / 민수 A등급 / 사용자 설정 선택과 함선별 수동값 복원이 되는가.
- 동일 품목·동일 크기의 독립 미션 ID와 상자 수량이 보존되는가.
- 84 SCU × 2 예시를 168 SCU·28상자로 유지하는가.
- 하역·되돌리기·현재 위치 재계산에서 실린 상자 위치가 유지되는가.
- 지상기지·스테이션 선택, 게이트웨이 경유, 간편 경로가 작동하는가.
- 파이로/스탠턴/닉스 배경이 구분되고 항성이 흰색으로 날아가지 않는가.
- 320/390px 모바일과 데스크톱에서 가로 넘침·버튼 가림·콘솔/셰이더 오류가 없는가.

v3.5.0 기능 변경 시 Node 22에서 전체 자동 테스트 116개가 통과했다. 출발·포드 적재·위키 매칭·파트너별 경로 검사도 포함한다. 이전 브라우저 검증은 별도 로컬 도구로 수행했으며, 그 도구의 절대 경로를 Cloud에서 전제하지 않는다. Cloud에서 사용 가능한 브라우저 도구로 위 시나리오를 재검증한다.
