# 추적 중 계약 수락과 누락 목표 복구

2026-11-03. 사용자 제공 Claude 조사 메모와 현재 구현을 대조했다. 원문 코드나 게임 원문 번역 파일을 가져오지 않았다.

## 확인한 것

- [SC Hauling Tools](https://sc-hauling.tools/)의 Game Watcher 설명을 직접 읽었다. 다른 계약이 mobiGlas에서 추적 중이면 뒤에 수락한 계약의 목표 줄이 기록되지 않을 수 있으며, 다음 계약 수락 전에 추적을 해제하라고 안내한다. **해당 도구의 관측/안내이며 모든 빌드의 보장된 게임 동작이라는 뜻은 아니다.**
- 사용자도 추적 중 다른 계약을 받으면 게임 내 알림이 울리지 않았던 것 같다고 보고했다. 이는 정황 근거이며 수락 당시 추적 상태와 로그를 통제한 재현은 아직 없다.
- 이미 제공된 로그34개에서 마커 줄841개를 확인했고 모두 `contractDefinitionId` 필드가 있었다. 실행 계약 `missionId`와 정의 ID는 별개로 파싱한다. 제목만으로 위키 유형을 고르는 방식으로 되돌리지 않는다.
- 같은 자료의 한국어 수락 알림2,508줄은 기존 parser에서 처리하는 문장 형식이다. 파일 사이 중복을 포함한 관측 줄 수이며, 서로 다른 미션 수가 아니다. 영어만 처리하는 parser가 아니다. 다른 한국어 패치 파일을 읽어 패턴을 만드는 방식도 도입하지 않았다.
- 현재 state는 실행 계약 ID별로 이벤트를 모으므로 뒤늦게 들어오는 목표·마커를 결합할 수 있다. 수락만 있고 운송 마커가 없는 계약이 화면에 보이지 않던 빈틈을 이번에 보완했다.

- 34개 파일에서 `TrackMission`, `SetTracked`, `MissionSelected` 및 mission/track 인접 표현을 찾아봤지만 직접 추적 켜기/끄기를 뜻하는 줄은 찾지 못했다. 이 검색만으로 그런 로그가 게임에 존재하지 않는다고 단정하지 않는다. 추적 전환→목표 재출력의 인과관계도 아직 미확인이다.

## 사용자 추가 확인과 검증 보류

사용자는 앞선 중형·대형 시험에서도 **추적을 끄지 않고 연속 수락했다**고 확인했다. 따라서 ‘추적 중이면 항상 새 계약 목표가 누락된다’고 단정할 수 없다. 이전 파일마다 중형/대형의 수량 알림 유무가 달랐으며, 수락 순서·추적 전환·재접속 등의 조건을 분리한 실게임 재현은 아직 없다. 이 조사는 지금 반복하지 않고 [최종 검증 L01~L03](FINAL-GAME-VALIDATION.md)에 남겨 구현 작업을 계속한다.

## 복구 동작

1. 수락 또는 확인된 본인 참여가 있지만 마커가 없으면 `pendingContracts`에 표시한다. 운송인지도 미확인이므로 운송 계획이나 운송 계약 통계에 섞지 않는다.
2. 같은 ID에 운송 마커가 들어오면 기존 기록을 운송 계약 목록으로 옮긴다. 다른 유형임이 확인되면 운송 대기 목록에서 제외한다. 내부 원래 관측은 삭제하지 않는다.
3. 부분 목표만 있으면 해당 계약만 보류한다. 나머지 준비된 계약은 계속 사용할 수 있다. 새 목표/좌표/수량이 들어올 때마다 기존 정의/공개 자료/고정 프로필을 다시 대조한다.
4. 검증된 대형은 수량 알림이 없더라도 확인된 정의·빌드·목적지 마커와 기존 사용자 검증 프로필이 충분하면 원래 명세를 연결한다. 이 예외를 다른 유형에 일반화하지 않는다.
5. 준비된 계약의 원래 명세가 바뀌지 않는 반복 마커·목표 진행 알림은 기존 경로·캔버스·예상 이동을 초기화하지 않는다. 상태/참여/빌드/충돌/실제 계획 입력이 변하면 다시 판정한다. 현재 aboard나 실제 배송 완료를 자동으로 채우지는 않는다.
6. 종료·이탈 기록은 늦은 마커로 되돌리지 않는다. 동일 유형의 다른 실행 ID와 혼합하거나 SCU 총량을 합쳐 복원하지 않는다.

## 사용자 안내와 한계

- 이미 받은 계약을 포기하거나 다시 받도록 요구하지 않는다.
- 해당 계약을 직접 추적으로 전환해 새 목표가 기록되는지 확인할 수 있지만 **전환 시 기존 목표가 다시 출력된다는 보장은 아직 없다.** 앱은 새 줄이 나타나면 자동으로 결합한다.
- 다음 계약 수락 전 기존 계약 추적 해제는 위 도구가 안내하는 예방 방법이다. 현재 누락 원인을 앱이 추적 상태 때문이라고 확정하지 않는다.
- 게임이 기록하지 않은 정보를 로그 읽기만으로 만들어낼 수는 없다. 부족한 필드의 공개 규칙·선택적 OCR·사용자 확인은 별도 보완 경로다. 미확인 수량이나 크기를 확정 데이터로 입력하지 않는다.
- 앱은 게임 추적 설정을 조작하지 않는다. 명령 자동 입력·후킹·패킷/메모리 읽기를 추가하지 않는다. 원문 로그와 플레이어 계정 ID는 외부 전송하지 않는다. 실행 계약 ID는 이 기기에서 관측을 결합하는 데 필요하다.

## 조사 메모에서 구분할 주장

| 메모 내용 | STAM 반영 |
|---|---|
| MissionId가 위키 유형 번호인지 미확인 | 우리 로그에서는 실행ID와 `contractDefinitionId`를 각각 확인·사용하고 있음 |
| 실제 상자는 랜덤이므로 미리 확정할 방법 없음 | 전체 유형에 대한 단정은 근거 부족. 검증된 고정 프로필1개는 지원하고 다른 유형은 계속 조사 |
| 직전 계약과 Awarded를 순서로 연결 | 채택하지 않음. 여러 계약/파티가 겹치면 미배정 수입으로 남길 계획 |
| 퀀텀 도착으로 접수/배송 자동 처리 | 도착과 화물 이행은 다르므로 단독으로 처리하지 않음 |
| 픽업 목표 완료 = 전량 함선 적재 | 실제 의미·소유·계약 귀속 검증 전 aboard 확정에 사용하지 않음 |
| 재접속 시 목록 복원 | 뒤늦은 관측은 결합하되 목록 미출현만으로 계약 삭제/포기 처리하지 않음. 영구 세션 복원은 별도 작업 |
| 먼저 새 영어/한글 로그2개 요청 | 기존 제공 자료를 먼저 사용. 부족한 이벤트가 명확해질 때만 필요한 추가 자료 요청 |

GPL 도구의 코드를 복사하지 않았다. 외부 서비스의 기능 존재를 CIG 공식 허용으로 표현하지 않는다. 전체 기능 목록과 남은 계정/위치/상자 작업은 [재구축 작업 목록](REBUILD-FEATURE-TRACKER.md)을 따른다.

## 2026-11-04 후속 연결

계약별 `수신 정보`를 펼치면 유형·픽업·배송·품목/총량·자동 상자 구성 중 연결된 항목을 볼 수 있다. 좌표 일치는 관측된 목표 기준이며, 그 개수가 계약 전체 목표 수라고 단정하지 않는다. 일반 부분 예약은 일부 화물이라고 표시하고 전체 항로를 보류한다. 수락 대기에서 운송 계약으로 이동할 때 같은 실행 ID의 펼침 상태도 유지한다.

운송 안내 중 새 계약이 준비돼도 자동 선택하지 않는다. 파트너는 다음 계획 대기로 안내하며 기존 운송 단계·선택·캔버스를 유지한다. 사용자가 해당 계약을 직접 선택하면 기존 계산 경로로 다시 계획한다. 이미 선택된 계약의 충돌/수요 변경은 그대로 재검증한다. 종료/참여 이탈한 계약은 정보 대기 건수에서 제외한다.
