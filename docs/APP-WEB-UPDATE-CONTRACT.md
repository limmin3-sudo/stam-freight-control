# 앱과 관제 업데이트 분리

사용자 결정: 사이트의 디자인·경로 계산·적재 3D·계약 화면을 업데이트해도 앱을 다시 설치하지 않는다. 앱은 Windows 실행기, 로컬 로그 수집/연결, 브라우저 자원 보관을 담당한다. 이용안내 최종 제작은 기능 확정 뒤 진행한다.

## 각각의 버전

- 사이트: 기존 사이트 버전/배포 커밋. Pages 빌드의 `web-release.json`에는 브라우저 파일 목록·바이트 수·SHA-256·호환 브리지 프로토콜·스냅샷 스키마를 기록한다. 내용이 바뀌면 별도 관제 릴리스 ID가 바뀐다.
- 앱: `desktop/version.json`. 사이트 버전에서 가져오지 않는다. Windows 패키지 작업도 사이트 버전 변경만으로 실행하지 않는다. 현재 프로토콜은 1이다.
- 디자인·경로/적재 계산·브라우저에서 처리하는 데이터 변경은 사이트만 배포한다. Windows 실행기나 로그 수집 인터페이스 변경이 필요할 때만 앱 버전을 올린다. 호환되지 않는 인터페이스를 기존 프로토콜 번호로 배포하지 않는다.

## 실행과 적용

1. 앱 실행 시 보관한 관제의 모든 파일을 확인한다. 이상이 있으면 이전 정상 관제, 그것도 없으면 동봉 관제로 시작한다.
2. 로그 연결과 화면을 먼저 열고, 고정된 공식 Pages 주소의 업데이트 목록을 백그라운드로 확인한다. 개인 로그/파일 경로/연결 토큰을 보내지 않는다.
3. 바뀐 자원만 다운로드한다. 변경 없는 영상·OCR 모델은 다시 받지 않는다. 파일별 크기/해시 검증을 전부 마친 뒤 준비된 버전 표시를 교체한다.
4. 현재 실행의 정적 파일 목록은 고정한다. 새 화면은 **다음 앱 실행**부터 사용한다. 자동 새로고침, 진행 중 항로 교체, 저장 데이터 초기화는 없다.
5. 사이트가 더 새로운 브리지 프로토콜을 요구하면 현재 관제를 유지하고 앱 업데이트 필요 상태만 알린다. 일반적인 UI/경로 변경에 이 조건을 사용하지 않는다.

캐시는 사용자 로컬 앱 데이터의 `STAM/web`에 둔다. 새 버전 검증 중에는 현재/이전/준비된 관제에 필요한 파일을 유지하고 나머지 오래된 자원을 정리한다. 연결 주소/포트와 브라우저 저장소 키를 변경하지 않는다.

## 경계와 실패 처리

- 다운로드한 JavaScript는 브라우저 자원이다. Node에서 import/실행하거나 네이티브 프로그램을 교체하지 않는다.
- 고정 HTTPS 출처만 사용하고 리다이렉트는 거부한다. 경로 이동, 네이티브 실행 파일, 제한 초과 파일/목록을 거부한다.
- 네트워크 장애·손상·중단·호환 불일치로 현재 화면/로그 감시를 중단하지 않는다. 다른 릴리스의 누락 파일을 동봉본에서 섞어 제공하지 않는다.
- 배포 후 버그 수정은 사이트 자원 재배포로 전달한다. 저장 형식 변경에는 별도 호환/마이그레이션 검증이 필요하며 이 업데이트 기능 자체는 사용자 저장 데이터를 수정하지 않는다.
- 최초 분리 기능이 없는 과거 시험 앱은 이 기능이 포함된 앱으로 한 번 교체해야 한다.

## 검증과 게시

`tests/web-update.test.mjs`: 다음 실행 적용/실행 중 버전 유지, 변경분 다운로드, 오프라인, 미래 프로토콜, 부분 수신/해시 오류, 손상 캐시 복구, 경로 검증, 기존 인증 API 유지와 파일 혼합 방지.

`STAM_WEB_RELEASE=<공개 빌드 경로> node scripts/check-unified-deck-browser.mjs`: 실제 배포 자원을 캐시에 받아 동일 브리지로 실행하며 중형+직접 입력 계약, 경로, 적재, 재접속을 확인한다.

현재는 작업 브랜치 구현이다. main/Pages 및 Windows 패키지 게시 승인 범위가 열리기 전에는 공개 업데이트 목록을 배포하지 않는다. 실제 Windows 실행과 공개 Pages 다운로드는 최종 검증에 남긴다.
