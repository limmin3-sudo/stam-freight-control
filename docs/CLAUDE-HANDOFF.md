## 반드시 보존할 확정 사항

1. **수석 항해사(`standard`)**: 기존 묶음 운송. 같은 픽업지에서 가능한 화물을 모으고 재방문·불필요한 항성계 왕복을 줄인다. `route-search.mjs`·`route-cost.mjs`의 기존 탐색은 그대로 유지했다.
2. **브리지 오퍼레이터(`aide`)**: `delivery-first.mjs`. 소량의 간단한 계약 완료를 우선하되 가까운 픽업도 챙긴다. 무조건 배송만 하는 방식이 아니다. 우회·작업 시간의 누적 한도는 우선 계약 예상 이동 시간의 25%, 최대 5분이며 우선 화물 적재 공간을 보존한다.
3. **밀수 브로커(`broker`)**: 파이로 초상화와 준비 중 소개만 구현. 순서는 오퍼레이터 → 항해사 → 브로커. 소개는 열리지만 다음 진행은 차단하며 활성 운송 파트너를 브로커로 바꾸지 않는다. 무역 API/추천 기능은 미구현이다.
4. **출발지 = 1번 단계**. `route-departure.mjs`는 기존 계획 앞에 출발 단계만 붙인다. 첫 픽업까지 이동선·거리·시간을 유지하며 첫 픽업을 출발 위치로 저장하지 않는다. 재개·재계산에서 기존 화물 소유권/좌표/완료 상태를 보존한다.
5. **냉동포드 1개 = 1 SCU**. 낮고 긴 `[1, 0.5, 2]` 셀, 수평 회전만 허용. 두 개 적층 시 일반 2 SCU 상자와 같은 외곽이다. 홀수 포드 위 또는 높이가 서로 다른 받침에 걸쳐 일반 상자를 올리지 않는다. 포드가 있을 때만 세로 반 셀 해상도로 검사한다. API의 `reportedVolumeScu:2`를 개당 화물량으로 적용해 총량을 두 배로 만들면 안 된다.
6. 위키 유형 매칭과 실제 상자 확인은 다르다. 안내창에 매칭 유형·픽업지·품목별 계산·출처를 표시한다. 저장값을 이번 계약만 위키 기준으로 되돌릴 수 있고 공유 레시피는 지우지 않는다. 편집하지 않은 자동 추정값을 실제 확인값으로 학습시키지 않는다.
7. 계약·shipment·개별 box 소유권을 유지한다. 같은 상품/크기라도 다른 계약 화물로 대체하지 않는다. 미션·진행·설정을 조용히 초기화하지 않는다.

## v3.6.0 텍스트 입력 후속 수정

`---` 없는 여러 미션을 한 계약으로 합쳐 위키 매칭이 실패하던 문제를 수정했다. `ocr.mjs`의 `splitMissionText`가 새 제목을 기준으로 분리한다. HTML 줄바꿈/마크다운 제목/줄 끝 역슬래시를 정리하고 독립된 `¤ 금액`도 인식한다. 기존에 합쳐져 저장된 계약은 자동 분할하지 않으므로 해당 항목 삭제 후 재입력해야 한다. `tests/text-intake.test.mjs`와 빈 저장소의 실제 브라우저 입력으로 확인했다.

## 현재 화면과 계정

- 왼쪽 **운송 시작**을 강조하고 **운송 계약 추가**는 일반 버튼이다. 한글/영어 부분 검색 → 출발지 선택 → 파트너 재확인 → 계약/상자 검토 → 브리핑 순서다.
- 운항 파트너 초상화 카드는 지도 좌측 STARMAP 아래에 있으며 관제 모드에서도 같다. 옛 상단 파트너 변경 버튼은 제거했다.
- 파트너 소개는 가상 경력 대신 기능을 각자의 말투로 설명한다. 영어 모드도 함께 유지한다.
- 계정 창에 누적수입·거리·운항/계약 수·시간·운송량과 완료 운항기록 초기화가 있다. 초기화는 확인 후 `sfc-history`만 비우며 현재 운항·미션·설정은 유지한다. 과거 거리 미기록 운항은 거리 합계에서 제외한다.
- Firebase 선택 로그인·계정 동기화는 구현돼 있다. 사용자가 Firestore 규칙 게시와 피드백 수신을 확인했다. 게스트/계정 분리와 충돌 선택을 유지한다. 이번 Codex 작업에서 실제 Google 로그인·다른 기기 동기화를 새로 검증한 것은 아니다.
