## 실제 로그

개인 첨부의 실제 `.log` **37개**를 앱의 실제 `receipt-log.worker.mjs`로 읽었다. 별도 텍스트 첨부 2개까지 포함한 초기 자료 탐색은 약 102MB였다. 원본·플레이어/계정 정보·실제 수주 인스턴스 ID·개인 파일 경로를 저장소와 공개 검수 산출물에 넣지 않는다.

| 전체 파일 끝까지 읽은 결과 | 수 |
| --- | ---: |
| 수신 기록 | 378 |
| 현재 계산 가능한 계약 | 7 |
| 정보가 불완전한 계약 | 58 |
| 종료 관찰 | 312 |
| 충돌 관찰 | 1 |
| 파일 읽기 오류 / 혼합 플레이어 차단 | 0 / 0 |

**378은 중복 파일을 포함한 기록 수이며 고유 미션 378개라는 뜻이 아니다.** 파일 끝에서는 이미 종료된 미션이 많으므로 수주 당시 prefix와 이후 append를 구분한다. 이벤트 회수/배달처럼 일반 운송 정의·SCU·거점이 없는 기록에 수량이나 경로를 만들어 넣지 않는다. 불완전한 기록을 읽은 것을 적재 계산 성공으로 세지 않는다.

실제 활성 운송 계약 1건은 사용자가 체크하는 동작부터 진행했다. **운송 항목 4개 / 합계 9 SCU / 방문 6곳 / 점프 포함 완료 조작 7회 / 최종 잔여 화물 0**을 확인했다. 실제 파일 → Worker → 미션 카드 선택 → 항해사 계획 → 지도 → 상시 적재 관제 → 완료까지의 저장 로그 재생이다. 실제 게임을 실행하거나 화물 이동을 실시간 감지한 검증은 아니다.

재현용 스크립트는 `scripts/check-private-game-logs-browser.mjs`다. 개인 로그 폴더를 `STAM_PRIVATE_LOG_ROOT`로 전달한다. Vite 개발 서버의 실제 Worker를 사용한다. 입력 원문과 파일명/경로를 결과에 복사하지 않고 파일 순번·집계와 동작 결과만 출력한다. 브라우저 파일 핸들의 append/중복/종료/수신 중지는 저장 로그와 테스트 파일 핸들로 검증하며 Windows 권한/실게임 감시와 구분한다.

## 다음 기능 작업 순서

1. 실제 로그 자동 수신의 Windows 실사용 검수와 불완전한 계약의 보완 흐름을 우선한다. 앱 자체 개편은 보류 상태를 유지한다.
2. 전체 세션 파일 복원은 후속 구현 완료(미배포). 사용자 정의 그리드 편집 UI는 후속 사용자 결정으로 제외하며 기존 데이터 호환성은 유지한다.
3. 아카이브 내부 미션 조회는 PR #31로 통합했다. 필드별 출처/서로 다른 값 대조도 현재 작업본에 구현했다. [검증](function-review-20261113/archive-reference/README.md). 운송 팁·가이드는 나중에 별도 센터로 만들며 이용안내 개편은 보류한다. 기존 자료 접근은 유지한다. 새 시설 입체 허브는 계획 단계다.
4. 지도/적재의 고해상도 원본과 실제 GPU 프레임 시간·메모리·장시간 동작을 확인한다. 소프트웨어 Chromium 결과를 사용자 기기 성능으로 확대하지 않는다.

위 목록은 우선순위 제안이며 현재 검토를 넘어선 앱 개편·새 연출·전체 기능 구현·main 배포의 자동 승인이 아니다. 사용자 최신 지시가 있으면 그 범위를 우선한다.
