## 사용자 목표와 반드시 지킬 결정

게임에서 운송 계약을 받으면 필요한 화물·총량·픽업/배송지·상자 구성을 연결하고, 파트너별 경로와 적재 3D를 준비한다. 정보를 일일이 다시 입력하는 흐름을 줄이는 것이 목적이다. 미확인 값을 맞는 것처럼 넣지 않는다.

- 게임 로그는 읽기 전용. 메모리/프로세스 주입/패킷 감청/자동 입력/게임 파일 수정/EAC 우회 금지. RSI 로그인 정보 수집 금지. 다른 도구가 한다는 이유로 CIG 허용이라고 단정하지 않는다.
- 공개 출처와 이용 조건을 확인한다. 원본 게임 번역 파일·사용자 로그·개인 식별자·스크린샷을 커밋하거나 외부로 자동 전송하지 않는다.
- 구 한글 패치 의존은 새 앱에서 제외한다. 기존 운영 화면의 호환 래퍼는 아직 남아 있다. SC-KoChat 번역 사용 방식과 출처 위치는 사용자 확인 전 도입하지 않는다. 영어/한영/한글 모드와 패치 독립 사용은 남은 작업이다.
- 대화는 짧은 반말, UI는 자연스러운 존댓말. 번역투를 싫어한다. [문구 기준](UI-VOICE.md)을 따르며 고유명은 영어를 기준으로 한다.
- 원래 화면 배치를 보존한다: 좌측 계정/준비/계약, 중앙 큰 지도와 아래 적재 3D, 우측 방문/작업 순서. 관제 모드는 기존 구도를 살리고 같은 렌더러를 재사용한다.
- 로그인·동기화·기존 사용자 데이터·업데이트 기록·파트너/초상화 유지. 수석 항해사 묶음 수거와 오퍼레이터 배송 완료 우선 정책을 보존한다.
- Hull B 목적지별 인접 블록, 모든 함선의 그리드 사용 선택, 실제 aboard 위치 보존, 냉동포드 1개=1SCU/반높이 규칙을 유지한다.
- 지도 예상 이동과 실제 위치 동기화를 구분한다. 로그 연결만으로 위치 동기화 표시를 켜지 않는다. 예상 도착/다음 구간 버튼은 배송·수입·실제 적재 기록을 만들지 않는다.
- main 반영은 사용자가 배포를 요청할 때만. 시험 브랜치 작업은 기존 승인 범위에서 진행하되 커밋/푸시 전 내용을 설명한다.

## 마지막 작업의 구체적 연결

- 재개: `progress.mjs`/`progress-view.mjs`를 parser→state→view에 연결. 계약 실행/목표 ID로 분리하고 완료·실패와 지급 알림을 표시한다. 구체적 근거는 [목표·종료·지급 조사](LOG-PROGRESS-EVIDENCE.md). 원래 명세/실제 함선 적재/계정 수입과 별도다. 아래 항법 연결은 이전 작업이며 보존했다.

- `integration/log/navigation.mjs`: 세션/항법 목표/퀀텀 도착/조종권 해제/창고 조회 파싱, 입력·세대·차량별 후보 상태, 신선도 정책. 기존 `parser.mjs` → `state.mjs` → `view.mjs` → `flight-ready.mjs`에 연결했다.
- 최근 2분 내 현 로그 관측만 후보로 제안한다. 이는 UI 만료 정책이며 게임의 정확도 보증이 아니다. 연결 중단·일시정지·파일 교체·미래 시각·과거 파일 재생은 적용 대상에서 제외한다.
- 적용 버튼을 누르기 전에는 계정 계획 설정을 쓰지 않는다. 운송 안내 중에는 적용을 차단한다. 로그 후보가 이미 확인한 계획을 자동 덮어쓰지 않는다.
- 공개 클래스 대응: Hull B, Starfarer, Aurora Mk II, Salvation의 기존 프로필. Centaurus는 이름만 확인했으며 다른 Constellation의 적재칸으로 대체하지 않는다.
- 최근 창고 정거장 4후보: Baijini Point, Seraphim Station, Everus Harbor, Port Tressler. 코드 대응은 StarCargoTracker의 커뮤니티 자료이며 화면에 출처를 표시한다. 본인 위치로 확정하지 않는다.
- 제공 34로그 파싱: 세션34, 목표248, 도착165, 해제234, 창고782건. 처음 세션 뒤 공백 차이로 34건 보류를 발견해 수정; 수정 후 해당 형식 오류0. 원본 파일 간 중복은 포함한다.
- 개인 이름/세션ID/엔티티ID/동적 비콘명은 공개 스냅샷·화면·계정에 내보내지 않는다. 엔티티 대응은 메모리 내부에서만 한다.
- 상세 근거·출처·제약: [함선·위치 조사](SHIP-LOCATION-EVIDENCE.md), [출항 준비 흐름](FLIGHT-READY-FLOW.md).

## 재개할 때 할 일

1. 현재 요청을 읽고 브랜치·작업 트리·upstream·최신 CI부터 확인한다. 기존 미커밋 작업을 보존한다. 이 문서 이전 상태로 되돌리지 않는다.
2. 후보 단계 다음으로 **본인 조종/정박 근거·지원 클래스/장소 대응을 확대할 수 있는지 검증**한다. 필요 근거가 없으면 미확인 유지. 모든 사용자에게 수동 재입력을 요구하는 화면을 기본 흐름으로 만들지 않는다.
3. 목표·종료·지급 표시는 연결했다. 다음은 실제 운항의 **잔여 화물·보상 귀속/기록·세션 복원**을 원래 계약 요구량/예상 이동과 분리해 연결한다. 여러 계약 완료 뒤 보상을 순서만으로 확정하지 않는다. 실린 화물의 위치·소유권·진행을 새 계획으로 초기화하지 않는다.
4. 일반 미션의 주문→거점 배분과 상자 구성 근거를 확대한다. 보조 OCR은 허용됐지만 오류/누락을 확정값으로 처리하지 않는다. 원본 유형 목록 전체 보유와 모든 명세 자동 해석을 혼동하지 않는다.
5. 이후 언어/SC-KoChat 사용 확인·기존 패치 제거 마무리, 설치형 런타임 포함 배포·포트 간 게스트 데이터 이전을 진행한다. Node22/24/26 호환을 유지하되 모든 과거 버전 지원을 보장하지 않는다.
6. README·LICENSE·출처 문서는 완성된 기능/설치 방식/실제 재사용 자료 기준으로 정리한다(사용자 요청). 필수 제3자 저작권 표시는 유지하며 구 패치 의존을 제거한 뒤 관련 안내를 정리한다.
7. 최종 실게임 검증은 [최종 목록](FINAL-GAME-VALIDATION.md)을 사용한다. 사용자는 중형/대형을 추적 해제 없이 연속 수락한 적이 있다. 추적 중 수락이 항상 누락 원인이라고 단정하지 않는다. 지금 같은 시험을 다시 요구하지 않는다.
