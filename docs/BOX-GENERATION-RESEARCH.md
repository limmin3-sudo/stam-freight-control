# 미션 ID로 실제 상자 구성을 찾는 조사

2026-11-03 · 조사 대상 게임 빌드 12913470 · 시험 브랜치 전용.

**후속 확인:** 사용자가 두 유형의 반복 고정성을 확인하고 대형의 실제 크기별 개수를 제공했다. 대형 1개 유형은 [고정 상자 프로필](FIXED-BOX-PROFILES.md)로 연결했다. 아래 ‘검증 후보’는 그 확인 이전의 공통 생성 규칙 조사이며, 이번 확인으로 다른 유형까지 검증된 것은 아니다. CSV의 `unverified`는 공개 데이터만 검사하는 감사 결과이므로 사용자 실게임 확인 건수와 구분한다.

## 현재 결론

미션 정의 ID로 **개별 주문의 품목·수량 범위·상자 상한**까지 찾는다. 상자 상한은 계약 전체나 품목 전체에 하나로 적용하는 값이 아니다. 작은 상자 수십 개가 필요한 계약도 개별 주문의 제한을 보존해야 한다.

공개 자료에서 실제 게임의 **상자 생성 알고리즘 전체**를 확인하지는 못했다. 따라서 아래 데이터와 계산 예를 실제 상자 명세로 승격하거나 적재 엔진에 전달하지 않았다. 이 조사의 미완료 항목은 상한·잔량 처리·주문 분리·특수 화물 규칙을 검증하는 것이다. 사용자에게 규칙을 찾아오도록 넘기는 것이 아니다.

원본은 각 주문에 `minSCU: N, maxSCU: 0`을 갖고 있다. SCMDB 화면 코드는 이 경우 N으로 표시한다. 이 표시 관행만으로 모든 계약의 0을 고정 수량으로 해석하지 않는다. 두 계약의 총량은 별도로 사용자 확인이 있다.

SCMDB의 법적 안내는 프로젝트와 기반 Star Citizen Wiki 자료에 CC BY-SA 4.0을 표시한다. 여기서는 출처와 조사 사실만 기록하며 원본 데이터 파일을 복제·배포하지 않는다. API와 SCMDB가 같은 게임 정의에서 유래할 수 있으므로 두 사이트의 일치를 독립적인 실게임 검증으로 세지 않는다.

## 검증해야 할 계산 가설

비교 대상 [SuperCargo의 공개 계산 코드](https://github.com/AquatikJustice/SuperCargo/blob/6d088e78255de4e5cd07e6dd9b63fa6e671ee9bc/src/shared/box.ts)는 상한 이하의 32/24/16/8/4/2/1 SCU 크기에서 큰 것부터 잔량을 분해한다. 이는 **다른 도구가 사용하는 공식**이며 게임 구현의 증거는 아니다. 코드를 복사하거나 확정 규칙으로 채택하지 않았다.

이 가설을 개별 주문에 적용하면 다음 검증 후보가 생긴다. 실제 상자 개수로 사용하면 안 된다.

- 대형 Medical Supplies: 주문당 20 SCU, 상한 2이면 `2 SCU × 10개`가 두 주문에 생기는 후보다. 합계 20개의 작은 상자가 된다. 계약의 다른 품목 상한인 16을 적용하면 틀린 결과가 나온다.
- 중형 Nitrogen: 주문당 12 SCU를 분해하면 `8 + 4`가 두 세트인 후보다. 주문을 먼저 합쳐 24 SCU로 만든 뒤 `8 × 3`으로 분해하는 것과 다르다. 총 SCU가 맞더라도 실제 상자 구성은 틀릴 수 있다.
- 상한 2만으로 `2 × 10`이 확정되는 것은 아니다. 예를 들어 `1 × 20`도 상한과 총량을 만족한다. 게임의 최대 크기 우선 생성 여부가 검증되어야 둘 중 하나를 선택할 수 있다.
- 냉동포드 같은 특수 화물에는 일반 SCU 컨테이너 분해를 적용하지 않는다. 기존 사용자 확인 규칙(개당 1 SCU, 반 높이, 홀수 높이 위 일반 상자 지지 금지)을 보존한다.

## 주문과 픽업·배송 연결에서 발견한 누락과 충돌

[ScDataDumper의 Contract 변환 코드](https://github.com/octfx/ScDataDumper/blob/120a728639bdd1b06525a0f8574cb0e91d0fbf8d/src/Formats/ScUnpacked/Contract.php)는 템플릿의 hauling objective를 읽고 주문에 `PickupPool`/`DropoffPool`을 연결한다. 상자 생성 개수 알고리즘은 이 변환 코드에서 확인되지 않았다. 추출기를 실행하거나 로컬 게임 파일을 읽지는 않았다.

2026-11-03 조회한 [중형 공개 JSON](https://github.com/StarCitizenWiki/scunpacked-data/blob/master/contracts/6f207f9c-0575-4a88-82f8-ccc348eab9da.json)과 [대형 공개 JSON](https://github.com/StarCitizenWiki/scunpacked-data/blob/master/contracts/461d27cf-9431-4391-89e9-288b3a424385.json)에서는 다음을 확인했다. 이 저장소의 조회 파일 자체에서 게임 빌드는 확인하지 못했으므로 같은 빌드로 간주하지 않는다.

- 대형: 첫 세 주문은 `PickupLocation → DropoffLocation1`, 다음 세 주문은 `PickupLocation → DropoffLocation2`로 연결되어 있다.
- 중형: 첫 세 주문의 DropoffPool이 `PickupLocation2`이고 다음 세 주문에는 연결이 없다. 실제 로그의 픽업 2곳·배송 1곳과 그대로 대응하지 않는다. 변환기의 연결 추론 오류 가능성이 있으나 원인을 확정하지 않았다. 주문 인덱스로 임의 보정하지 않는다.
- Wiki API 응답은 이 연결 필드를 제공하지 않는다. 공개 자료에 정보가 없는 경우와 API 변환에서 빠진 경우를 구분해야 한다.
- 위 JSON의 hauling objective UUID는 로그 목표 ID 안의 UUID와 일치한다. **정의의 objective UUID와 실행 계약 ID는 다르다.** objective UUID만으로 같은 유형을 여러 번 수락하거나 파티 공유한 계약을 합치면 안 된다. 숫자 접미사를 곧바로 주문 배열 인덱스로 해석해서도 안 된다.

## 전체 목록의 실제 범위

### 2026-11-03 후속 변환 코드 검토

위에 고정한 ScDataDumper 커밋의 `buildHaulingOrderRoutingMap` / `decodeRoutingEdge`를 다시 확인했다. 각 edge에서 참조 인덱스의 기준값 후보를 순회하고, pickup/dropoff가 cargo 변수가 아닌 위치에 들어가는 첫 후보를 반환한다. 모든 edge가 같은 기준값을 공유하는지는 이 함수에서 검증하지 않으며 결과는 cargo 변수 키로 저장된다. 여러 후보의 의미가 올바른지까지 검증하는 게임 런타임의 원본 연결은 이 코드만으로 알 수 없다. 공개 테스트는 합성 두 배송 묶음을 검사하지만, 문제가 있는 중형의 실제 템플릿 fixture는 확보하지 못했다.

따라서 중형의 잘못된 `DropoffPool=PickupLocation2`와 두 번째 주문 묶음의 연결 누락을 우리가 주문 순서로 보정하지 않는다. 공개 SCMDB의 현재 빌드 주문 6개도 품목·수량·상한은 제공하지만 픽업별 연결은 제공하지 않는다. 실제 템플릿의 신뢰할 수 있는 공개 연결, 또는 해당 실행 계약의 품목별 픽업 할당 근거가 더 필요하다. 단일 주문도 로그에서 현재 마커 2개가 보인다는 사실만으로 전체 topology가 확인되었다고 승격하지 않는다. 이번에 자동 연결 유형을 늘렸다고 보고하지 않는다.

재생 명령: `node scripts/audit-log-box-coverage.mjs`.

[유형별 CSV](audits/mission-box-coverage.csv)와 [요약 JSON](audits/mission-box-coverage.json)은 기존 Wiki 인덱스의 공개 정의 1,840개를 중복 ID 없이 분류한다. 공개 변형·특수 화물·미출시 항목을 포함하므로 **현재 게임의 모든 활성 운송 미션을 확보했다는 뜻이 아니다.**

| 분류 | 정의 수 | 의미 |
|---|---:|---|
| 단일 수량 표시 + 지원되는 상자 상한 | 54 | 우선 조사 대상. 실제 구성 확정 수가 아님 |
| 가변 수량 + 지원되는 상자 상한 | 618 | ID 외에 실행 시 정해진 수량이 필요 |
| 상자 상한 해석 미지원 | 635 | -1 등. 기본값 32로 대체하지 않음 |
| 특수 화물 또는 혼합 주문 | 476 | 일반 SCU 분해와 별도 처리 |
| 주문 없음 | 50 | 공개 목록만으로 명세를 만들 수 없음 |
| 선택 주문 | 7 | 실행 시 선택된 가지 확인 필요 |

예: `00dbf460-b432-4e52-8f04-1283f35849ac`의 Stims 주문은 80–112 SCU, 상한 8이다. 상자 생성 방식이 밝혀져도 ID 하나가 이번 수량 80과 112 중 무엇인지 알려주지는 않는다. 실제 수량 알림 등 실행 증거와 결합해야 한다.

## 다음 검증과 적용 조건

1. 공개 주문 원본과 API 변환을 대조하여 상한 상속, 선택 주문, 특수 아이템을 구분한다. 자료에서 해석하지 못한 값은 별도 상태로 남긴다.
2. 게임의 생성 방식에 대한 공개 구현·명시적 설명 또는 해당 빌드의 직접 관측으로 최대 크기 우선/잔량 처리/주문 분리 가설을 검증한다. 다른 플래너의 공식을 게임 규칙의 증거로 대체하지 않는다.
3. 특히 작은 상자 대량 생성, 같은 품목의 반복 주문, 24 SCU 상한, 잔량과 특수 화물을 반례 검사에 포함한다. 수량 합계만 같은 것을 통과로 보지 않는다.
4. 검증된 규칙을 추가할 때는 게임 빌드·정의 ID·주문별 입력·근거를 함께 저장한다. 변동 입력이 로그에 없으면 다른 계약의 값을 재사용하지 않는다.

현 시험판의 `manifest: null`과 적재 계산 차단은 유지된다. 이번 결과는 조사/분류 자료이며 새 시험판 실행이나 반복 계약 수락을 요구하지 않는다.

## 후속 공개 소스 및 전체 로그 재검색

- [sc-item-stat-updater의 템플릿 추출 코드](https://github.com/Amoenus/sc-item-stat-updater/blob/2af035301c7e0aedd3c5539870768a973e2f66b8/src/sources/datacore/contract-template-hauling-extractor.ts)도 리소스·수량 범위·상자 상한을 추출한다. 실제 분해 알고리즘의 공개 구현은 이 파일에서 확인되지 않았다. 코드를 읽었으며 추출기는 실행하지 않았다.
- 사용자 로그 34개, 98,598,436바이트를 재검색했다. `SMarkerHandler_Hauling::OnItemRegistered` 63줄은 작은 배송 물품/특수 아이템 클래스였다. 이번 일반 SCU 운송의 전체 상자 명세로 연결되는 기록은 찾지 못했다. 엘리베이터 요청 개수나 인벤토리 결과 개수를 해당 계약의 상자 수로 대체하지 않았다. `CargoSystemUtilities::FindBoxSize`의 냉동포드 리소스 컨테이너 없음 오류도 있어, 일반 자원 컨테이너 계산을 특수 물품에 적용하지 않는 기존 제약을 유지한다.
