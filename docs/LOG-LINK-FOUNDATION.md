# 로그 연동 1단계 — 관측·검증 기반

## 현재 범위

재구축 작업 브랜치의 개발용 기능이다. 운영 앱·계정 저장·경로·적재 엔진에 아직 연결하지 않는다. **실시간으로 모든 실제 화물 정보를 복원하는 완성품이 아니다.**

현재는 `start-log-link.cmd` 또는 `scripts/log-link-server.mjs`로 수집기와 브라우저를 실시간 연결할 수 있다. 사용자 실행 순서는 [집에서 테스트하는 방법](LOG-LINK-TESTING.md)을 따른다.

- 사용자가 명시한 로그만 읽는다. Node 수집기는 `open(path, 'r')`로 열고 256 KiB씩 증분 처리한다. 게임 서버/외부 네트워크 전송·게임 프로세스·메모리·입력·게임 파일 쓰기·디렉터리 자동 탐색을 사용하지 않는다. 실시간 브라우저 연결은 해당 PC의 `127.0.0.1` HTTP에 한정한다.
- 수락 알림의 실행 미션 ID와 `HaulCargo` 템플릿 마커의 정의 ID를 연결한다. 제목 유사성만으로 운송 계약으로 분류하지 않는다.
- 종료·목표 상태·수량 알림·구역 좌표는 **관측 기록**으로 보존한다. 마커 위치를 현재 함선 위치나 특정 거점으로 추정하지 않는다.
- 한 목표에 여러 품목이 나오는 경우 알림을 각각 보존한다. SCU 합산·품목 ID 추정·픽업지 균등 배분·상자 추정은 하지 않는다.
- 공개 정의의 품목/최대 수량을 실제 계약에 채워 넣지 않는다. `manifest`는 `null`, `planning.allowed`는 `false`이다. `requireVerifiedManifest()`는 호출자 플래그와 관계없이 현재 단계에서 항상 차단한다.
- 정의 ID 충돌·종료 상태 충돌·종료 후 수락 관측은 충돌 상태로 남긴다. 동일 내용·동일 시각의 이벤트는 백업 파일에 반복돼도 중복 적용하지 않는다.
- 공유 알림은 참여가 아니다. 같은 로그 세대의 `STATE_CURRENT` 캐릭터 GEID와 참여/탈퇴 주체를 대조한다. 다른 파티원의 참여·탈퇴·종료는 본인의 행동으로 쓰지 않는다. 같은 유형의 서로 다른 실행 ID는 별도 계약이며, 같은 실행 ID의 재수락/재참여는 이력을 보존한다.
- 파서가 모르는 형식이나 잘못된 UTF-8은 진단 횟수를 남긴다. 손상된 줄의 문자를 대체하거나 추정해 입력하지 않는다. 마지막 개행 없는 줄은 미완성 가능성이 있어 보류한다.

기존 앱의 예상 구성 기능은 이 실험 기능과 연결되지 않는다. 앞으로 실제 연동 어댑터를 만들 때 기존 자동 추정 경로를 통과시키면 안 된다. 현재 게이트를 해제하려면 아래의 완전성 검증이 먼저 필요하다.

## 실행

Node.js 22, 저장소 루트에서:

```sh
node scripts/log-link.mjs --file "선택한/Game.log"
node scripts/log-link.mjs --file "선택한/Game.log" --watch
node scripts/log-link.mjs --file "선택한/첫째.log" --file "선택한/둘째.log"
```

기본 출력은 집계만이다. `--json`은 미션 실행 ID와 관측 알림을 포함하므로 개인 정보로 취급하고 공개 이슈/커밋에 첨부하지 않는다. 감시는 파일 하나만 대상으로 하며 Ctrl+C로 중단한다. 250ms 간격으로 순차 확인하고, 읽을 내용이 없으면 전체 스냅샷을 다시 계산하지 않는다. 파일 잠김·읽기 오류는 중단하고 알리며 부분 결과를 적재에 넘기지 않는다.

별도 파일을 브라우저에서 재생하는 검증 화면:

```sh
npm start
```

`http://127.0.0.1:4173/log-link.html`을 열어 로그를 선택한다. 이 화면은 **파일 재생**이며 지속 감시 화면이 아니다. 선택한 파일은 브라우저에서만 처리한다. 네트워크는 같은 서버의 화면 모듈·공개 정의 인덱스 GET 요청뿐이고 로그 업로드·계정 동기화·localStorage 저장은 없다. 기존 앱의 메뉴에는 연결하지 않았다. 현재 한국어 개발 화면이며 제품의 새 3개 언어 모드는 후속 작업이다.

### 실시간 연결

```sh
node scripts/log-link-server.mjs --file "선택한/Game.log" --open
```

Node 22의 내장 모듈만 사용한다. 별도 npm 설치·prepare/Three.js 다운로드·게임 파일 추출은 필요 없다. Windows 실행 도우미는 OS 파일 선택창으로 로그를 고른 뒤 같은 명령을 실행한다. 파일 선택창 PowerShell 문법은 검사했지만 실제 Windows 대화상자 조작은 미확인이다.

- 서버는 `127.0.0.1`의 임의 포트에만 바인딩한다. 공개 웹사이트/휴대폰에서 연결하는 기능이 아니다. `Host`·`Origin`·`Sec-Fetch-Site` 검사, 실행마다 새 256비트 연결 키, API Authorization 헤더, POST 제어의 동일 Origin 검사를 적용한다. CORS를 허용하거나 브라우저 보안을 끄게 하지 않는다.
- 서버는 시작 시 선택한 경로만 읽는다. HTTP로 경로를 변경하거나 파일 내용을 쓰는 API는 없다. 정해진 화면 모듈만 제공하며 `Game.log`·서버 코드·다른 파일은 정적 경로로 제공하지 않는다.
- 연결 키는 시작 주소 fragment로 브라우저에 전달하고 주소창에서 제거한다. 새로고침 재연결을 위해 해당 로컬 origin의 sessionStorage에만 둔다. 화면 연결 해제 시 삭제하며 계정 동기화/요약 파일에 포함하지 않는다. 서버 재시작 시 이전 키는 무효다.
- 250ms 증분 수집, 전경 500ms/숨긴 탭 2초 상태 확인, 다시 보이면 즉시 확인. 동시 폴링을 막는다. 계약 관측/진단이 바뀔 때만 스냅샷을 만들고 캐시하여 노이즈 줄마다 계약 전체를 전송하거나 다시 렌더하지 않는다. 읽는 중에는 작은 바이트 조각마다 이벤트 루프를 양보한다.
- 일시정지/재개, 파일 교체·잠김·누락 재시도, 마지막 읽기 시각, 연결 끊김 표시를 지원한다. 해석/메모리 상한 오류는 감시를 중단하고 마지막 정상 스냅샷만 보존한다. 오류 직전에 일부 처리된 변경은 새 결과로 게시하지 않는다. 스냅샷 JSON은 8 MiB 상한이다.
- 원문 없는 요약 저장은 집계·진단·충돌 횟수·연결 상태만 브라우저에서 내려받는다. 계약 제목·실행 ID·캐릭터 ID·로그 경로·연결 키는 제외한다. 자동 외부 전송은 없다.

한 번에 파일 64개/합계 512 MiB, 입력 조각 1 MiB 이하, 한 줄 128 KiB, 이벤트 100,000개/미션 10,000개/직렬화된 근거 UTF-16 길이 환산 32 MiB를 상한으로 둔다. 초과 시 명시적으로 중단한다. 근거 크기 상한은 실제 프로세스 메모리 보장값은 아니다. 화면은 50개씩 표시하고 상세 내용은 열 때 만든다.

## 로그 형식의 확인 범위

사용자가 제공한 빌드 `12913470`의 31개 로그에서 확인했다. 테스트에 커밋한 내용은 동일 문법으로 만든 가상 데이터이며 원본 로그·개인 ID·파일 경로는 커밋하지 않는다. 한국어 수락 문구는 사용자 로그 문법을 인식하는 것으로, 한글 패치 사전 데이터를 가져온 것이 아니다.

| 태그 | 추출 필드 | 해석 한계 |
|---|---|---|
| `SHUDEvent_OnNotification` | 수락 제목, MissionId, ObjectiveId, SCU 현재값/총량 알림 | 알림 하나가 계약 전체 화물 명세는 아님. 한국어와 영어 수락 접두어 지원, 영어 실게임 미확인 |
| `CLocalMissionPhaseMarker::CreateMarker` | 실행 ID, 정의 ID, 템플릿, 목표 ID, zoneHostId, 좌표 | 거점명·품목·실제 함선 위치로 자동 해석하지 않음 |
| `EndMission` | 실행 ID, CompletionType, 내부 대조용 PlayerId | 다른 사람의 종료는 내 종료로 반영하지 않음. 이름·사유 텍스트는 버리고 주체 ID는 스냅샷에서 제거 |
| `ObjectiveUpserted` | 실행 ID, 목표 ID, 상태 | 완료된 목표를 실제 상자 위치/적재로 변환하지 않음 |
| `AccountLoginCharacterStatus_Character` | 내부 대조용 geid, state | STATE_CURRENT만 신원 근거. 이름/accountId는 보존하지 않음. 다른 입력·세대·미래 시점에서 빌려오지 않음 |
| `MissionShared` | 실행 ID, 내부 대조용 ownerId | 공유자 정보이며 수신자의 참여를 뜻하지 않음 |
| `PlayerJoined` / `PlayerLeft` | 실행 ID, 내부 대조용 player_id | 본인과 타인 구분 후 이력 보존. 태그·본문 종류 불일치 또는 잘못된 ID는 거부 |

`MissionEnded`, 함선 탑승·위치·보상은 추가 조사 후보이며 이번 파서에 구현하지 않았다. UI의 ‘수락/참여/탈퇴 기록 관측’은 마지막으로 관측된 이력이며 현재 활성 계약의 완전 목록을 확정하지 않는다.

### 파티 공유와 본인 구분

- 본인 식별은 계정 비밀번호나 RSI 조회 없이 같은 로그의 캐릭터 상태 기록만 사용한다. ID는 숫자 변환 없이 문자열로 비교한다. `STATE_UNSPECIFIED`, 신원 줄 누락, 파일 세대 변경, 이벤트보다 나중의 신원 기록은 본인 확정에 쓰지 않는다.
- 여러 입력에서 서로 다른 로그인 캐릭터 GEID가 나오면 입력 묶음 전체를 충돌로 표시하고 본인 구분을 보류한다. 같은 계정의 캐릭터 변경일 수도 있으므로 ‘서로 다른 계정’으로 단정하지 않는다.
- 공유 알림+마커만 있거나 다른 사람의 참여만 있으면 후보에 남긴다. 수락 알림 또는 신원이 대조된 본인 참여 기록이 있을 때만 등록된 관측 계약에 포함한다. `acceptedHauling`은 HUD 수락만, `registeredHauling`은 본인 참여 근거로 등록된 경우도 포함한다.
- 같은 실행 ID의 탈퇴 이후 재수락/참여는 새 계약으로 복제하지 않는다. 제목/유형이 같은 다른 실행 ID는 합치지 않는다. 동일 시각의 참여/수락과 탈퇴가 충돌하면 순서를 추정하지 않는다.
- `PlayerLeft`는 참여 이탈 관측이다. 직접 포기·추방·완료 후 정리 중 어느 원인인지 이 줄만으로 단정하지 않는다. 화면에서는 참여 이탈로 표시한다.
- `Abandon`과 `Complete`가 함께 있는 경우 재수락 이력으로 설명될 가능성이 있어도 종료 의미를 확정하지 않는다. 기존 종료 충돌 표시는 유지한다.
- 캐릭터 GEID·공유자/참여자 ID는 메모리 내부 대조에만 사용하고 UI·스냅샷/CLI JSON에는 `self`/`other`/`unknown`으로 표시한다. 스냅샷의 실행 미션 ID·알림 문장은 여전히 개인 자료다.
- 실제 31개 로그: STATE_CURRENT 30개 파일, STATE_UNSPECIFIED 1개 파일, 확인된 로그인 캐릭터 GEID는 한 종류. 운송 계약 102건 중 공유 관측 19건, 본인 참여 이탈 관측 33건, 이탈 뒤 재수락 1건. 해당 계약들에서 타인 참여 42건·타인 탈퇴 12건을 본인 상태와 분리했다. 본인 PlayerJoined는 이번 실자료에 없으며 가상 로그로 분기만 검증했다.

## 공개 정의 인덱스와 출처

- 출처: [Star Citizen Wiki API](https://api.star-citizen.wiki/developers).
- 공개 버전: `4.10.2-LIVE.12881860`. 제공 로그 빌드와 다르므로 실제 상태의 근거로 승격하지 않는다.
- `has_hauling && released && !not_for_release` 대표 361개와 연결 변형을 합쳐 ID 1,840개. 변형의 미출시 표시 54개도 보존한다. SCU 운송 외 미션 아이템을 포함하는 넓은 후보 목록이며 게임의 모든 활성 계약 목록이라고 보증하지 않는다.
- 인덱스는 공개 정의의 식별·참고용이다.

별도로 확보한 공개 응답에서 재현하는 명령:

```sh
node scripts/build-log-index.mjs --cache <공개_API_응답_폴더> --index <public-catalog-index.json> --output data/log-mission-index.json
```

이 빌더는 다운로드·게임 파일 추출을 하지 않는다. 입력 인덱스는 `{definition_id, representative_ids, version}` 배열, 응답 파일은 `<definition_id>.json`이다. 버전·응답 ID·중복을 검사하고 승인된 필드만 출력한다. 운영의 기존 일일 갱신 작업과 아직 연결하지 않는다.

다음은 집에서 실게임 관측을 대조하고 지원 버전/세션/파티 참여 목록의 완전성을 검증하는 단계다. 로컬 연결과 공유·본인/타인 관측 구분은 구현했지만 실게임의 모든 전이와 현재 참여 목록을 검증한 것은 아니다. 현재 수집기는 재시작 시 선택 파일을 처음부터 재생하며 영구 체크포인트는 없다. 파일 교체는 파일 식별자·축소·끝부분 변경으로 감지하지만 임의의 동일 길이 중간 수정 전체를 검출하는 감사 도구는 아니다. 체크포인트·게임 세션 식별·누락 구간 복구 검증 전에는 현재 활성 목록으로 확정하지 않는다.

정확한 자동 적재를 허용하려면 계약별 전체 목표, 품목별 실제 수량, 픽업/배송 할당, 실제 상자 규격별 개수를 확인할 근거가 모두 필요하다. 로그·공개 정의·선택적 OCR이 충돌하면 보류한다. 최대 SCU나 최대 상자 크기를 실제값으로 바꾸는 방식은 금지한다. 이 기준을 통과하기 전에는 현재의 계산 차단을 해제하지 않는다.
