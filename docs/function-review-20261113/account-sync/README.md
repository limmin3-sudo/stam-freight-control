# 진행 중 운항 계정 동기화 점검 — 2026-11-13

기능 클라우드 `integration/freight-division-20261113`, `b1abe51` 이후 작업본. 이번 턴은 **현행 코드 대조·문제 재현·구현 순서 설계**다. `account.mjs`, `sync.mjs`, Firestore 규칙이나 제품의 계정 동작은 수정하지 않았다. 앞선 미커밋 기능 작업을 보존했고 커밋·푸시·배포하지 않았다.

## 재현한 문제

### 1. 다른 계정 데이터를 선택해도 이전 운항이 남음

합성 계정 A의 선적/진행이 있는 브라우저에서 계정 B 로그인 상태를 제공하고 실제 계정 창의 ‘계정 데이터 불러오기’를 눌렀다. 기존 미션 키는 B 것으로 바뀌지만 새 콘솔의 운항 키와 이전 백업은 A 상태로 남았다. 로그아웃 후에도 같은 운항이 남는다.

원인은 운항이 `SYNC_KEYS` 밖에 있어 `snapshot`의 게스트 백업에도 없고 `applySnapshot`이 교체/분리하지 않기 때문이다. 서버가 다른 UID의 데이터를 허용했다는 의미는 아니다. **브라우저 안의 운항 소유권이 계정 전환과 분리되지 않는 문제**다. 이후 완료 기록이 현재 계정의 기록에 합쳐질 수 있는 연결도 코드상 남아 있다(완료 기록 오귀속은 이번 브라우저 시나리오에서 직접 실행하지 않음).

### 2. 두 기기의 동시 저장을 놓침

같은 계정의 두 합성 브라우저가 같은 저장 시각 100을 읽게 한 뒤 각각 다른 미션 자료를 저장했다. 실제 `account.mjs`가 두 번 모두 batch 저장을 승인하고 각 기기의 마지막 저장 자료를 갱신했지만 모의 서버에는 한쪽 자료만 남았다.

`cloudStamp` 읽기와 `push`의 `writeBatch`가 분리되어 있다. 확인 뒤 저장 전 다른 기기가 저장해도 배치 내부에서 다시 검사하지 않는다. `Date.now()` 기반 비교는 서로 다른 기기 시계의 역전/동일 시각에도 충돌을 놓친다.

### 3. 용량 초과를 삭제와 구분하지 못함

`cleanValue`는 900,000자보다 크면 null을 반환한다. `snapshot`은 해당 키를 생략하고 `changedKeys`는 기존 값이 없어졌다고 판단한다. 이 결과를 기존 `push`에 전달하면 삭제 경로가 된다. 이번 순수 저장소 모델에서 950,000자 값의 생략 및 변경/삭제 대상 판정을 재현했다. 실제 Firebase 삭제는 실행하지 않았다.

또 제한은 UTF-8 바이트가 아닌 JavaScript 문자열 길이다. 한글 400,000자(1,200,000바이트)가 이 검사에서는 통과했다. 새 운항은 전체 백업 상한이 20MB이며 경로별 배치/선적 이력을 포함하므로, 이 함수에 운항 키를 추가하는 방식으로 연결하면 안 된다.

## 추가 코드 대조 사항 — 실계정 재현과 구분

- `account.mjs`는 인증 변경 시작 시 기존 타이머를 즉시 멈추거나 진행 중 요청을 세대 번호로 무효화하지 않는다. `tick`/`useCloud`/`useLocal`은 비동기 처리 사이에 변하는 `user.uid`를 참조한다. 계정 분리 작업에서 함께 보완해야 한다.
- 계정 ‘이 브라우저 데이터로 덮어쓰기’는 로컬/클라우드 키 합집합을 쓰고, 로컬 스냅샷에 없는 키는 삭제한다. 새 운항을 기존 `users/{uid}/state`에 넣으면 **이전 버전 클라이언트가 모르는 새 키를 삭제할 수 있다**. 별도 저장 경로/버전 경계를 설계해야 한다.
- `applySnapshot`은 여러 localStorage 키를 순서대로 바꾸며 중간 실패 시 롤백하지 않는다. 계정 전환 중 저장 실패도 재현/대응 범위에 포함해야 한다.
- 저장소의 `firestore.rules`는 UID별 접근을 제한하지만 새 운항 전용 경로/버전/크기 규칙은 없다. 저장소 규칙을 읽었을 뿐 **실제 배포된 보안 규칙은 확인하지 않았다**.
- ‘동기화됨’ 상태는 최초 클라우드 조회 성공/충돌 판단 전에 표시될 수 있다. 연결됨·확인 중·저장됨·충돌/실패를 구분해야 한다.

## 권장 구현 순서와 완료 기준

### 1단계: 계정/게스트 운항 분리와 저장 방어

`account.mjs` 인증 진입부에서 이전 자동 저장을 즉시 멈추고 UID+요청 세대를 고정한다. 인증이 바뀐 뒤 도착한 응답이 새 계정 자료를 바꾸지 못하게 한다. 중복 tick도 한 번에 하나만 실행한다.

`use-flight.ts`의 현재 운항/이전 백업/선택 계약을 계정 UID 또는 게스트 소유로 보존한다. 기존 소유자 정보 없는 운항은 보존본을 만든 뒤 연결을 선택하게 하고 자동으로 새 계정 소유로 지정하지 않는다. 계정 변경 중 저장에 실패하면 기존 운항을 유지하며 새 계정으로 업로드하지 않는다. 로그 수신함의 탭 한정 보관은 그대로 유지하되 수신했다고 자동으로 새 계정 운항에 넣지 않는다.

완료 기준: A→B→게스트→A 왕복에서 각자의 운항/선적/이전 백업이 보존된다. 변경 중 늦은 응답·중복 요청·저장 실패·로그아웃에서도 계정 간 섞임/자동 업로드가 없다.

### 2단계: 충돌을 저장 순간에 검사

기기 시각 대신 서버 문서의 정수 리비전을 사용하고, 마지막 확인 리비전과 현재 리비전 비교 및 저장을 **동일 Firestore 트랜잭션**으로 처리한다. 충돌하면 기존 로컬/서버 자료를 유지한 채 사용자 선택을 기다린다. 명시적 ‘이쪽 사용’도 확인창을 연 뒤 서버가 다시 바뀌면 재확인한다.

운항은 이전 클라이언트의 일반 상태 전체 덮어쓰기와 분리된 저장 경로를 사용한다. 큰 운항은 검증 가능한 불변 분할 사본을 먼저 저장하고, 완전한 사본만 트랜잭션으로 현재 버전으로 지정하는 설계를 권장한다. 크기 초과/일부 업로드 실패를 삭제로 변환하지 않는다. UTF-8 크기·총량·조각 수·체크섬을 검증한다. 계정별 접근 규칙/소유자 검증과 함께 설계·테스트해야 하며 실제 규칙 배포는 별도 작업이다.

완료 기준: 두 브라우저가 같은 리비전에서 동시에 저장하면 한쪽만 현재 버전을 갱신하고 다른 쪽은 충돌 안내를 받는다. 느린/빠른 기기 시계에도 결과가 같다. 업로드 실패/과대 자료는 마지막 정상 서버 사본을 유지한다.

### 3단계: 확인 후 이어서 운항

로그인 후 현재 기기와 계정 운항의 함선·파트너·현재 목적지·선적/보류 SCU·완료 단계·저장 기기를 비교한다. ‘계정 운항 이어하기’ 또는 ‘현재 기기 운항 유지’를 선택한다. 자동으로 현재 선적을 바꾸거나 진행 타이머를 재개하지 않는다.

기존 `flight-backup.ts`의 검증/일시정지 복원과 `use-flight.ts.prepareRestore`의 변경 여부 재확인을 재사용한다. 확인 시 양쪽 리비전/운항이 바뀌었으면 적용하지 않는다. 좌표 사본·계약 소유권·보류 화물·미확인 로그 변경·완료 기록까지 같은 운항 단위로 보존한다.

처음 계정 연결과 충돌 선택을 마친 뒤에만 해당 소유자의 자동 저장을 활성화하는 방향을 권장한다. 새 설정 패널을 늘리기보다 기존 계정/운항 관리에 넣는다. 계정 연결 자체는 선택 사항이다.
