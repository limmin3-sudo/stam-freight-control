# 계정별 운항 보관·동시 저장 방어 — 2026-11-13

`integration/freight-division-20261113`, `b1abe51` 이후 기존 작업을 보존한 미커밋 변경. 커밋·푸시·main/공통 인계 반영·배포하지 않았다. 앞선 [수정 전 점검](../account-sync/README.md)의 계정 분리 문제와 기존 동기화 저장 경쟁을 수정했다. **새 콘솔 운항의 기기 간 클라우드 이어하기 구현은 아니다.**

## 실제 변경

- 현재 운항과 복원 전 백업을 게스트/계정별로 보관한다. 계정 전환 시 나가는 소유자의 두 자료를 보관하고 들어오는 소유자의 자료를 복원한다. A의 미전송 기존 미션·기록도 로컬 계정 보관본에 남겨 다음 A 로그인 때 비교한다.
- 소유자 표식이 없는 기존 운항은 `unassigned`로 원본을 보존한다. 로그인 때 ‘이 운항을 계정에 연결’ / ‘따로 보관하고 계속’을 선택한다. 대상 계정에 다른 운항/백업이 있으면 직접 덮어쓰지 않고 별도 보관 후 기존 백업 복원 흐름에서 검토하게 한다.
- 미션/관제의 ‘운항 백업 · 복원 → 로그인 전 운항 확인’에서 이전 미지정/게스트 운항을 검토하고 명시적으로 복원할 수 있다. 파일 백업과 이전 운항 확인은 유지한다.
- 인증 변경 시 타이머를 바로 중지하고 UID·요청 세대·로컬 소유자/메타데이터를 확인한다. 늦은 조회/저장 응답은 새 로그인에 반영하지 않는다. 이미 서버에 제출된 요청은 원래 UID에서 완료될 수 있지만 새 UID나 새 로컬 메타데이터로 옮기지 않는다.
- 인증 확인 중에는 운항 편집/진행/Worker 결과/백업 복원과 기록 삭제를 막는다. 다른 탭의 계정·운항 교체도 기존 화면에서 덮어쓰지 못하게 하고 새로고침을 안내한다. 현재 메모리 운항 백업 다운로드는 가능하다.
- 여러 localStorage 키를 바꾸기 전 원본을 저널에 보관한다. 쓰기 실패 시 롤백하며, 복구마저 실패하면 저널을 유지하고 다음 초기화에서 원본 복구를 재시도한다. 계정 보관본 손상은 무시하고 빈 자료로 덮어쓰지 않는다.
- 기존 계정 자료 저장은 `runTransaction` 안에서 리비전과 마지막 저장 시각을 비교하고 같은 트랜잭션으로 갱신한다. 동시 저장 하나만 성공하고 다른 쪽은 선택을 기다린다. 명시적 덮어쓰기/불러오기 선택 후 서버 자료가 또 바뀌어도 재확인을 요구한다.
- UTF-8 용량 초과는 오류로 중단한다. 누락/null로 바꿔 서버 자료를 삭제하지 않는다. 지원하지 않는 새 클라우드 키도 삭제하지 않는다. 썸네일 제외와 기존 동기화 대상은 유지한다.
- 계정 상태 문구를 ‘동기화 연결됨’/‘확인 필요’로 바꾸고 진행 중 새 콘솔 운항은 이 브라우저에만 계정별 보관됨을 계정 창에 명시했다. 승인된 테마·상단바·사이드바 배치는 그대로다.

## 파일

- `account.mjs`: 인증 전환·명시적 선택·계정 보관·타이머/응답 방어.
- `account-sync-transport.mjs`: 일관된 조회·트랜잭션 비교/저장.
- `flight-ownership.mjs` / `.d.mts`: 소유자/보관본·인증 전환 상태.
- `storage-transaction.mjs`: 다중 키 복구 저널.
- `sync.mjs`: UTF-8 상한·원자적 로컬 적용·기존 키 목록 유지.
- `apps/control-room/src/use-flight.ts`, `FlightBackup.tsx`: 계정/다른 탭 경계에서 운항 변경 차단·로그인 전 운항 검토.
- `history.mjs`: 인증 변경 중 기록 삭제/초기화/저장 방어.
- `tests/account-storage.test.mjs`, `tests/account-transport.test.mjs`, `tests/sync.test.mjs`: 실패 복구/소유권/경쟁/초과 크기 회귀.
- `scripts/check-account-sync-browser.mjs`: 실제 빌드·컨트롤러와 가짜 Firebase SDK/트랜잭션 저장소를 연결한 검수. 이전 audit 스크립트는 버그 재현 기록이므로 현재 통과 검사로 사용하지 않는다.

## 검증과 한계

- 전체 루트 247개 + 앱 78개 = 325개 통과. 이후 기록 방어 변경의 영향 범위인 기록·동기화 테스트 17개 재확인 통과.
- TypeScript/Vite 생산 빌드 통과. 기존 큰 번들 경고는 남아 있다.
- Chromium 생산 빌드에서 A→B→게스트→A의 현재/이전 운항 정확한 보존, 명시적 기존 운항 연결, 저장 실패 롤백, 인증 확인 중 잠금, 늦은 조회/저장 응답 무효화, 확인창 이후 서버 변경 재확인, 두 기기 동시 저장 하나만 승인 확인. `browser-check.json`, `account-a-restored.png` 참고.
- 기존 운항 변경 흐름도 생산 빌드에서 다시 검증했다. 2계약 선적 → 취소 알림/나중에 확인 → 오래된 확인 거부 → 저장 실패 복구 → 모바일 확인 → 남은 배송 → 16 SCU 선내 보류 → 새로고침 → 방문 0개 경로까지 통과했다(`receipt-regression.json`).
- 실제 Worker 응답을 보류한 동안 다른 탭의 운항 사본을 바꾼 회귀도 통과했다. 오래된 계산은 적용되지 않으며 새로고침 후 확인 재계산이 가능하다. 오퍼레이터 적재 미표시·항해사 적재 보존도 확인했다(`worker-race-regression.json`).
- 실제 Firebase 로그인/Google 팝업/실계정/배포 규칙에는 접근·저장하지 않았다. 브라우저 검수는 SDK 요청을 가로채 합성 계정에만 연결한다. 이 결과를 실서버 검증이라고 부르지 않는다.
- **Firestore 규칙은 이번에 변경·배포하지 않았다.** 새 클라이언트끼리의 트랜잭션 경쟁은 검증했지만, 예전 클라이언트가 리비전을 지키지 않고 별도 배치로 쓰는 행위까지 서버에서 강제 차단한 것은 아니다. 실제 배포 전 규칙의 리비전 강제와 이전 클라이언트 호환 정책/에뮬레이터 검증이 남았다.
- 브라우저 보관은 브라우저 저장 공간/사이트 데이터 삭제의 영향을 받는다. 작은 자료도 추가 사본/저널을 저장할 공간이 없으면 전환을 중단한다. 원본 백업을 지우며 공간을 확보하지 않는다.

## 다음 작업

1. 저장소 규칙의 리비전 강제 및 구형 클라이언트와의 공존 방안을 설계·에뮬레이터 검증한다. 실서버 배포는 별도 범위다.
2. 새 콘솔 전체 운항은 기존 `users/{uid}/state`에 단순 추가하지 않는다. 큰 운항/이전 백업을 별도 버전 경로에 완전한 사본으로 저장하고, 검사된 사본만 현재 리비전에 연결하는 저장 방식을 구현·검증한다.
3. 두 기기 운항 비교 → 사용자 선택 → 일시정지 복원으로 이어하기를 연결한다. 이미 실린/보류 화물·계약 소유권·좌표·완료 단계·개인 장소 사본을 그대로 유지해야 한다.
4. 사용자 실제 게임 실시간 검증은 당분간 보류한다. 팁 센터·이용안내 개편·로그 연결 앱 재작성도 기존 보류를 유지한다.
