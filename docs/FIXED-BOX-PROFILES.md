# 실게임 확인 고정형 상자 조합

2026-11-03 · `rebuild/log-evidence-foundation` 시험 기능.

## 근거와 적용 범위

사용자는 자주 수락하는 중형·대형 두 유형의 화물 조합이 반복해서 같았다고 확인했다. 같은 대형 계약에서 다음 크기별 개수도 직접 확인했다.

| 품목 | 확인된 구성 | 합계 |
|---|---|---:|
| Ship Ammunition | 16 SCU × 4개 | 64 SCU |
| Hydrogen | 16 SCU × 4개 | 64 SCU |
| Medical Supplies | 2 SCU × 20개 | 40 SCU |
| 전체 | 28개 | 168 SCU |

이 값은 일반 분해 공식의 결과를 사실로 표시한 것이 아니다. 사용자 실게임 확인과 반복 수락 경험을 근거로 저장한 **해당 유형의 품목별 전체 구성**이다. 현재 함선에 실린 수량, 현재 엘리베이터 인벤토리, 배송 완료 후 남은 수량을 뜻하지 않는다.

- 적용 정의 ID: `461d27cf-9431-4391-89e9-288b3a424385`.
- 적용 게임 빌드: `12913470`만. 로그의 `[CIG] build_version[...]`을 같은 입력/로그 세대에서 직접 확인한다. Wiki 버전·파일 이름으로 대신하지 않는다.
- 중형 `6f207f9c-0575-4a88-82f8-ccc348eab9da`는 고정형이라는 사용자 확인만 저장한다. 크기별 개수는 아직 제공되지 않았으므로 생성하지 않는다.
- 게임의 공통 최대 크기 우선 생성 규칙이나 모든 고정형/특수형 미션이 검증된 것은 아니다. 별도 유형은 이 조합을 상속하지 않는다.

## 동작

`integration/log/box-profiles.mjs`는 정확한 정의 ID·빌드·충돌 여부로 고정형을 조회한다. 대형의 SCU 알림이 없는 경우도 조회할 수 있다. 수량 알림이 있으면 이 유형에서 관측한 여섯 목표의 총량 32/32/20/32/32/20과 대조한다. 새로운 목표 ID나 다른 수량을 만나면 적용을 보류한다. 목표 인덱스를 다른 유형의 주문에 일반화하지 않는다.

관측된 목표 UUID는 공개 템플릿 ID이며 실행 계약 ID가 아니다. 두 개의 수락 또는 파티 공유 계약은 각각 자신의 실행 계약 ID를 품목 구성에 보존한다. 조합 객체를 공유하지 않아 하나의 수정이 다른 계약에 번지지 않는다.

`builds.mjs`는 입력 파일·로그 교체 세대별 빌드 근거를 분리한다. 빌드 누락, 계약보다 뒤에 나온 빌드 줄, 다른 빌드, 혼합 빌드에는 조합을 적용하지 않는다. 종료된 계약의 과거 조합을 표시하더라도 그 계약을 다시 활성화하지 않는다.

시험 화면에 **고정 상자 조합이 확인된 계약** 수와 품목별 크기·개수가 추가된다. 확인 출처를 표시하며 현재 인벤토리를 직접 읽은 것으로 표현하지 않는다.

## 목적지별 원래 계약 명세

`manifest.mjs`는 검증된 대형 유형에만 별도의 대칭 배송 묶음 규칙을 적용한다. 아래 세 근거를 함께 사용한다.

- [Star Citizen Wiki 공개 원시 정의](https://github.com/StarCitizenWiki/scunpacked-data/blob/1340c8303709904165e2da0fa7060bce0624260b/contracts/461d27cf-9431-4391-89e9-288b3a424385.json): PickupLocation 하나에서 DropoffLocation1/2 각각으로 탄약 32 / 수소 32 / 의약용품 20 SCU를 지정하는 여섯 주문. 해당 커밋 메시지의 버전은 **4.10.2-LIVE.12881860**이다.
- [동일 실행 빌드 SCMDB 공개 데이터](https://scmdb.net/data/merged-4.10.2-live.12913470.json): 여섯 주문의 수량·상한 일치. SHA-256 `72153c1ba58e497549628f134168c2f2c97b342c76e436292a304407a61a5186`. 이 자료에는 주문별 pool 연결이 없으므로 동일 빌드의 pool 연결까지 증명했다고 표현하지 않는다.
- 사용자 제공 대형 계약 원문들의 각 배송지 요구량도 32 / 32 / 20 SCU이며, 사용자 실게임 확인 상자는 전체 탄약 16×4, 수소 16×4, 의약용품 2×20이다. 반복 시 동일하다는 사용자 확인도 있다. 개인 원문/로그/ID는 저장소에 넣지 않는다.

두 배송 묶음의 구성이 동일하므로 두 관측 배송지 중 어느 쪽이 첫 번째 pool이든 필요한 상자는 같다. **총량을 배송지 수로 나눈 것이 아니다.** 서로 다른 묶음이나 다른 유형에는 적용할 수 없다. 대형의 관측 pickup 0 / dropoff 0·3 이외의 목표 집합, 위치 불일치·중복, 공개 후보 밖 지점, 상자 프로필 충돌에는 생성하지 않는다. 중형의 공개 pool 연결 충돌과 미확인 상자 개수는 그대로 보류한다.

결과 `originalManifest`에는 픽업 1곳과 배송 2곳, 목적지마다 탄약 16 SCU×2, 수소 16 SCU×2, 의약용품 2 SCU×10이 들어간다. 합계는 168 SCU/28개다. 같은 유형을 여러 번 받으면 실행 계약 ID별로 소유권을 분리한다. 공개 거점 XYZ의 유일 일치도 요구하지만 위치 API에는 버전 정보가 없다는 제한을 표시한다.

`originalPackingPreview(contract, index)`는 근거를 다시 검증한 뒤 기존 `makeShipments`/`packBoxes`가 받을 수 있는 명세를 만든다. SCU 우선 분해나 미확인 상자 기본값을 사용하지 않는다. 이 어댑터는 **원래 계약 요구량 미리보기 전용**이며 현재 실린 상자·남은 배송량을 나타내지 않는다. `manifest:null`, `planning.allowed:false`, `requireVerifiedManifest`의 실운항 변경 차단은 유지한다. 원래 명세 확인 수와 현재 운항 계산 가능 수를 혼용하지 않는다. 종료/이탈 계약도 과거 명세만 보존하며 다시 활성화하지 않는다.

시험 화면에는 목적지별 명세 표를 표시한다. 3D 렌더러 UI와 실제 운항 상태 반영은 아직 연결하지 않았다. 새 게임 수락 없이 기존 로그로 확인할 수 있다. 다음은 명세 미리보기의 3D 화면 연결 및 운항 상태를 훼손하지 않는 가져오기 흐름이다. 랜덤 수량·특수 물품은 [규칙 조사](BOX-GENERATION-RESEARCH.md)의 별도 검증 대상이다.
